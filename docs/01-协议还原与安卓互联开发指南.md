# 飞秋 FeiQ 安卓版 —— 协议还原与开发指南

## 2026-06-08 补充：文件夹传输、联系人分组与富文本

- 文件夹传输按公开 IPMsg 协议实现：附件清单中的目录条目使用 `IPMSG_FILE_DIR`，接收方拉取目录时使用 TCP `GETDIRFILES`，发送方返回 `header-size:filename:file-size:fileattr:content` 的层级流，并用 `IPMSG_FILE_RETPARENT` 返回上级。

- 联系人分组按 FeiQ/IPMsg 已确认字段实现：上线/应答附加段使用 `昵称\0分组\0`，Android 端按分组字段归类联系人。尾部 NUL 要保留，老 FeiQ 2013 可能继续向后读字段；分组消息对该分组成员逐个发送普通 `SENDMSG`，这不是电脑飞秋“新建群/群聊”协议。
- 电脑飞秋群聊仍未实现：群号、群名称、群密码、管理员密码、群简介、群公告、搜索/申请入群、成员管理、群消息等都属于另一套飞秋私有协议，必须抓包确认后再做。
- 富文本字体已按实测标签实现收发：文字正文后追加 `{/font;...;}`，接收时解析该标签并还原基础样式；搜索/通知/预览仍使用剥离标签后的纯文本。
- 头像仍未实现电脑端兼容：本地资料只有 COM `FaceImage` 属性和配置项，未确认 UDP/TCP 网络格式。必须抓 Windows 飞秋头像变更/刷新/上下线期间的 2425 包后再实现。

## 2026-06-08 补充：Windows 飞秋首张内联图片 15 秒延迟已修复

- 已确认这不是 Android 解码/UI 慢，而是 Windows 飞秋 UDP 图片分块窗口等待 ACK。
- 旧实现存在实际缺陷：一行损坏注释把第一遍 `udp.sendNow(ack, ip, srcPort)` 吞掉，导致“发两遍 ACK”的策略实际上只发了一遍；ACK 也在重组之后才发。
- 当前实现：收到 `0x2000C0` 分块后，先解析头部并立即发送 `0xC1` ACK，随后重组图片；首 160 块和每 32 块额外补发一次 ACK；`UdpChannel` 缓存 `InetAddress`，减少突发 ACK 的收包线程开销。
- 真机验证：2026-06-08 00:00，小米手机，Windows 飞秋发送第一张 96456 字节/189 块内联图片，完成用时 53ms，最大间隔 1ms，重复包 0。

## 二、IPMsg 协议总览

- **传输**：消息走 **UDP**，文件/文件夹走 **TCP**，默认端口都是 **2425**。
- **发现**：无服务器。上线时向 `255.255.255.255:2425` 广播；其他在线端回包，双方各自建立用户列表。
- **编码**：经典 IPMsg 用 SJIS；飞秋/国内环境用 **GBK/GB2312**；新版可带 `IPMSG_UTF8OPT` 用 UTF-8。安卓端建议：发包默认 GBK（兼容飞秋），收包按是否带 UTF8 标志选择解码。
- **可靠性**：UDP 无确认，靠 `IPMSG_SENDCHECKOPT` 要求回执 `IPMSG_RECVMSG`，超时重发。

### 报文格式（版本 1）

```
版本号 : 包编号 : 发送者名 : 发送者主机名 : 命令字 : 附加段
Ver(1) : PacketNo : SenderName : SenderHost : CommandNo : AdditionalSection
```

示例（发一条文字消息）：
```
1:100:shirouzu:jupiter:32:Hello
```
其中 `32` = `0x20` = `IPMSG_SENDMSG`（命令字在报文里通常是**十进制**字符串，是 32 位整数 = 命令 | 选项位 的结果）。

**分隔符规则**：`:` 是分隔符，用户名/主机名里若含 `:` 要替换（如换成 `;`）。文件名里含 `:` 用 `::` 转义。消息换行统一用 `\n`(0x0a)。

## 五、核心流程

### 1) 上线发现
```
本机启动:  广播 1:<pkt>:<user>:<host>:(0x01|能力位):<昵称>\0<分组>\0      → 255.255.255.255:2425
其他在线:  收到后单播 1:<pkt>:<user>:<host>:(0x03|能力位):<昵称>\0<分组>\0 → 本机IP:2425
本机:      收到 0x03，把对方加入用户列表
下线:      广播 1:<pkt>:<user>:<host>:0x02:<昵称>
```
- 扩展分组：在附加段昵称后加 `\0` 再加组名，并补尾部 `\0`。飞秋自己空分组的实测包是 `昵称\0\0`。
- 能力位：ENTRY 包里 OR 上 `IPMSG_FILEATTACHOPT`/`IPMSG_ENCRYPTOPT` 表示"我支持文件/加密"。

### 2) 收发消息
```
发送:  1:<pkt>:<user>:<host>:(0x20|0x00000100):正文      (要回执时 OR SENDCHECKOPT)
回执:  1:<pkt2>:<user>:<host>:0x21:<原pkt>                (对方收到后回送)
```
超时未收到回执则重发。封筒消息加 `SECRETOPT`，对方点开回 `READMSG`。

### 3) 文件附件（v9+）

发送方在 SENDMSG（OR 上 `FILEATTACHOPT`）的附加段里：**正文 + `\0` + 文件清单**。
文件清单格式（每个文件以 `\a`(0x07) 分隔）：
```
fileID:filename:size:mtime:fileattr[:扩展属性=值[,值…]]:\a:下一个fileID...
```
`size/mtime/fileattr` 为 16 进制；文件名含 `:` 用 `::` 转义。
`fileattr` 低 8 位：`IPMSG_FILE_REGULAR=1`(普通) / `IPMSG_FILE_DIR=2`(目录) / `IPMSG_FILE_RETPARENT=3`(返回上级) 等。

接收方下载单文件——**向发送方 TCP 2425 发起连接**，请求附加段（全 16 进制）：
```
1:<pkt>:<user>:<host>:0x60:<packetID>:<fileID>:<offset>
```
发送方校验后，把该文件从 offset 起的**裸数据**写回 TCP 流（无格式）。`offset` 用于断点续传。

接收方下载文件夹——用 `IPMSG_GETDIRFILES (0x62)`，附加段 `packetID:fileID`，发送方按层级流：
```
header-size:filename:file-size:fileattr[:扩展属性=值…]:文件内容
下一个 header-size:filename...
```
（除 filename 和内容外全 16 进制；`header-size` 是从它自己到内容前那个 `:` 的字节数。目录用 `DIR`，回上级用 `RETPARENT`，文件名固定为 `.`。）

### 4) 加密（v9+，可选，做"完整复刻"时再上）
RSA 交换公钥 + 对称密钥(RC2/Blowfish)加密正文。
`ANSPUBKEY` 附加段：`能力位:E-N`（E=指数,N=模数，16 进制，`-` 分隔）。
`SENDMSG|ENCRYPTOPT` 附加段：`能力位:被公钥加密的对称密钥:被对称密钥加密的正文[:签名]`。
> 飞秋私有加密可能与标准 IPMsg 不同，**强兼容时需抓包验证**。

## 六、★实测：飞秋真实报文（2026-06-03 抓包）

在你笔记本上启动 FeiQ.exe，用随机源端口向 `127.0.0.1:2425` 发 BR_ENTRY 探测，飞秋单播回的 ANSENTRY 原始字节：

```
1_lbt6_0#128#F8B46AA55B28#0#0#0#4001#9:1780525944:13652:DESKTOP-4331HHF:6291459:13652\0\0
```

按 `版本:包号:用户:主机:命令字:附加段` 拆解：

| 段 | 实测值 | 解读 |
|----|--------|------|
| **版本段** | `1_lbt6_0#128#F8B46AA55B28#0#0#0#4001#9` | ⚠️**飞秋私有扩展**！不是标准的 `1`。结构：`1`(IPMsg版本)`_lbt6_0`(飞秋标识，作者lbt)，再 `#` 分隔：`128` / **`F8B46AA55B28`=本机MAC** / `0#0#0` / **`4001`=端口或版本标识** / `9`(能力) |
| 包编号 | `1780525944` | 32位整数 |
| 用户名 | `13652` | 登录名 |
| 主机名 | `DESKTOP-4331HHF` | |
| **命令字** | `6291459` = `0x600003` | ANSENTRY(0x03) + FILEATTACHOPT(0x200000) + ENCRYPTOPT(0x400000)。飞秋声明支持文件传输+加密 |
| 附加段 | `13652\0\0` | 昵称=`13652`，`\0` 分隔后分组为空（再补一个 `\0`） |

**对安卓端的硬性结论：**
1. **版本段必须模仿飞秋格式** `1_lbt6_0#...#<MAC>#...#<端口标识>#<能力>`，否则飞秋可能不认/不回。纯标准 `1` 能收发基础消息，但要"完整复刻"互通需照抄此格式。安卓端需取本机 WiFi MAC（注意安卓6+ 默认返回 `02:00:00:00:00:00`，需用其他方式或随机稳定值）。
2. 命令字飞秋用十进制整数（`6291459`），与标准一致，✅ 我们的常量对得上。
3. **编码 = GBK**，分隔符 `:`，附加段 `\0` 分隔，✅ 已验证。
4. 飞秋默认开启 **FILEATTACH+ENCRYPT 能力声明**——基础文字互通不需要真加密，但 ENTRY 包最好也带上能力位以示兼容。

> 待补抓：①真人从飞秋发一条中文消息给安卓端，看 SENDMSG 附加段富文本/表情格式；②文件传输 TCP 流；③飞秋私有加密是否真启用（基础消息通常明文）。

### ★实测补充：飞秋的富文本字体标签（2026-06-03 真机）

手机给飞秋发 `1`、飞秋回 `1`，安卓端收到的 SENDMSG 附加段实际是：
```
1 {/font;-16 0 0 0 400 0 0 0 134 0 0 2 32 微软雅黑 8404992;}
```
即「正文 + 空格 + `{/font;...;}` 标签」。标签是飞秋私有富文本，内容是 Windows **LOGFONT** 结构：
`-16`=字号(lfHeight) `400`=字重(lfWeight,normal) `134`=GB2312字符集(lfCharSet) `微软雅黑`=字体名 `8404992`=文字颜色(RGB)。

**处理**：安卓端收消息时解析 `\{/font;...;\}`，记录原始字体字段并在聊天气泡尽量还原粗体、斜体、下划线、删除线、颜色和字号；搜索、通知和会话预览使用剥掉标签后的纯文本。
注意：`}` 在安卓 ICU 正则引擎里必须转义成 `\}`，否则启动崩溃。
发消息时默认附加同格式 `{/font;...;}`，电脑飞秋会按富文本样式显示；聊天页“文字格式”菜单可关闭或调整粗体、斜体、下划线、颜色、字号。

### ★实测补充：文件传输的 packetID 编码（2026-06-04 真机）

手机→飞秋发文件失败的根因：**GETFILEDATA 的 packetID 是十六进制**。
- 安卓发文件通告时用十进制包号登记（如 `169174`）。
- 飞秋来拉文件时，GETFILEDATA 附加段里 packetID 用 **16进制** `294d6`（=169174）。
- 两边不匹配 → TCP 服务器"找不到待发文件" → 接收失败。

**结论（验证了规范"GETFILEDATA 全16进制"）**：收到 GETFILEDATA 时，packetID/fileID/offset 都按 16 进制解析；与本地登记的十进制包号匹配前要先 `toLong(16)` 转换。双向文件传输修复后均成功（手机↔飞秋，1760字节完整无损）。

### ★★实测逆向：飞秋私有"内联图片"协议（2026-06-04 真机，完整破解）

飞秋粘贴/内联发图片**不走文件附件**，而是私有的 UDP 分块 + ACK 协议（即配置里的 `BmpUdpSendSize=512`）。完整三段：

**1) 标记包**（命令 `0x120` = SENDMSG）：正文里嵌占位符
```
/~#>64ea4edd<B~{/font;-16 0 0 0 400 ... 微软雅黑 8404992;}
```
`/~#>图片ID<B~` 表示"此处有内联图片，ID=64ea4edd"。接收端正则 `/~#>[^<]*<B~` 剥离。

**2) 分块包**（命令 `0x2000C0` = `2097344`，含 FILEATTACHOPT 位，低字节 `0xC0`）：
附加段 = `头部#\0二进制数据`，头部按 `|` 分隔：
```
图片ID|总字节|偏移|总块数|当前块(1基)|块大小|0|2|0|00000000
例: 64ea4edd|622241|0|1216|1|512|0|2|0|00000000
```
每块 512 字节，按偏移写入预分配缓冲，收满 总字节 即完成。

**3) ★ACK（关键！必须回，否则飞秋卡死）**：
接收端每收到一个分块包，**立即回**一个：
- 命令 = `0xC1`(193) = 分块命令低字节 `0xC0` + 1（**不带** FILEATTACHOPT 位）
- body = `图片ID|当前块#`（如 `64ea4edd|1#`），GBK，尾部带 `\0`
- 发到块的来源 ip:port

**逆向 ACK 格式的方法**：让安卓按此协议发图给飞秋，飞秋作为接收方回的包就是 ACK 模板（命令193, body `id|index#`），照抄即可。

**性能要点（踩坑）**：
- 飞秋一个窗口瞬间发~100块（51ms），接收端必须**逐块立即回ACK**。
- ACK 若用"每个起一个协程异步发"会在突发下大量丢失 → 飞秋每窗口超时15秒重发，奇慢。
- 修复：①ACK 在接收线程**同步直接发**；②**发两遍**兜底防丢；③加大 socket 收发缓冲(1MB)。
- 效果：修复后第2张起均~80ms秒到。**仅每次启动后第一张**因飞秋对新对端保守慢启动卡一次15s，之后全速（飞秋单方面机制，接收端难根除）。

### ★实测补充：飞秋内置表情码（2026-06-08 真机）

电脑飞秋发送内置表情时，不一定走图片/内联图片协议。用户实测：电脑发送第一个“微笑”表情，安卓收到正文为：

```
/:)
```

结论：

- 飞秋内置表情应按文本码处理，例如 `/:)` 映射到本地 `1.gif`。
- 安卓发送内置表情时也优先发送对应文本码，让电脑飞秋用自己的内置表情渲染。
- 自定义表情、图片表情或没有已知文本码映射的资源，才使用飞秋内联图片协议。
- 安卓聊天记录中用内部 token 保存混合内容，UI 渲染成图片；通知/搜索/预览显示为 `[表情]`。

### ★静态逆向补充：FeiQ.exe 内置表情 96 项码表（2026-06-08）

`FeiQ.exe` 的 UTF-16LE 字符串区包含一段 96 项纯表情码表，已由 `tools/feiq_pe_reverse.py` 提取到 `tools/feiq_reverse_report.json` 的 `emoticons.asset_map`。结合真机实测 `1.gif -> /:)`，可确认该表在二进制中按资源倒序存放；安卓 `FeiqEmoticons.kt` 已改为这份 FeiQ 静态码表，不再使用 QQ 猜测码表。

复核更新：静态码表里存在别名和内部顺序，不能单独作为电脑端面板显示顺序。2026-06-08 已用 `tools/feiq_tooltip_capture.py` 自动悬停电脑飞秋表情面板，采集 96 个 tooltip，结果保存在 `tools/feiq_emoticon_tooltips.json` 和 `tools/feiq_emoticon_tooltips.csv`。安卓最终采用 tooltip 实测顺序：16 列 x 6 行，`1.gif -> /:)`，`16.gif -> /<rotate>`，`89.gif -> /:baoquan`，`96.gif -> /:love`。

### ★实测逆向：飞秋原生"抖一抖"协议（2026-06-07 ADB 抓包确认）

电脑飞秋对安卓端发送一次"抖一抖"时，安卓 UDP 2425 收到：

```
cmd = 209 = 0xD1
base = 0xD1
opts = 0x000000
extra = 00
```

完整报文仍是 IPMsg/飞秋基础头：

```
1_lbt6_0#128#<MAC>#0#0#0#4001#9:<packetNo>:<user>:<host>:209:\0
```

抓包日志样例：

```
from=192.168.2.148:2425 cmd=209 base=0xD1 opts=0x000000 desc=0xD1 ... extraHex=00
```

结论：

- 发送抖一抖：向对端 UDP 2425 发送命令 `0xD1`，附加段为单个 NUL 字节。
- 接收抖一抖：收到低 8 位 `0xD1` 即触发本机振动/界面晃动。
- 抖一抖确认：安卓端发送 `0xD1` 给电脑飞秋后，电脑飞秋回 `cmd=210`、低 8 位 `0xD2`、附加段 `00`。安卓端当前只识别并记录该确认，不触发 UI。

## 七、飞秋私有扩展（需进一步抓包确认的部分）

公开 IPMsg 之上，飞秋扩展了：备注名、个性头像、个性签名、富文本/图文混排、群发、内置表情。这些**字段格式没有公开精确定义**，落在：
- `BR_ENTRY/ANSENTRY` 附加段：用户名后用特殊分隔符附加昵称/签名/分组/版本。
- 头像：通常走 TCP（类似文件），UDP 包里只给标志和元信息。
- 富文本图片：飞秋有 `BmpUdpSendSize=512` 这类 UDP 分片发图机制。

**抓包方法**（联调阶段做）：
1. Wireshark 过滤 `udp.port == 2425`，"Decode As" 文本按 GBK 看。
2. 两台装飞秋的机器互相上线/发消息/发文件，对照本文命令字逐字段比对。
3. 命令字 DWORD 与 `0x00400000` 做与运算判断是否加密；与 `0x00200000` 判断是否带文件。
4. 重点抓 `BR_ENTRY(0x01)` 看昵称/签名扩展段的真实分隔符。

## 七、安卓端架构建议

```
app/
 ├─ net/
 │   ├─ UdpChannel        # DatagramSocket，绑定2425，收发+广播(setBroadcast)
 │   ├─ TcpFileServer     # ServerSocket 2425，响应 GETFILEDATA/GETDIRFILES
 │   ├─ TcpFileClient     # 主动连对端下载文件
 │   ├─ Packet            # 序列化/解析 "Ver:Pkt:User:Host:Cmd:Extra"
 │   ├─ Command/Option    # 上面所有常量
 │   └─ Codec             # GBK/UTF-8 编解码
 ├─ core/
 │   ├─ PeerManager       # 用户列表(上线/下线/刷新/超时)
 │   ├─ MessageManager    # 发送/回执/重发/封筒
 │   └─ FileTransfer      # 续传、进度
 ├─ data/                 # Room: 联系人、消息、传输记录
 └─ ui/                   # 联系人列表 / 聊天 / 文件
```

**安卓平台要点（坑）：**
- **权限**：`INTERNET`、`ACCESS_WIFI_STATE`、`CHANGE_WIFI_MULTICAST_STATE`、`ACCESS_NETWORK_STATE`，安卓13+ 通知权限。
- **广播/组播锁**：收广播前 `WifiManager.MulticastLock.acquire()`，否则部分机型收不到 255.255.255.255。
- **后台限制**：安卓 8+ 后台无法长跑 socket，需 **前台 Service + 通知** 维持在线。
- **省电/Doze**：长连接会被杀，需 WakeLock / 前台服务，并处理断网重连、定时重广播刷新在线。
- **IP/广播地址**：用 `WifiManager` 的 DHCP 信息算子网广播地址（很多企业网禁 255.255.255.255，要用子网定向广播）。
- **编码**：默认 GBK 兼容飞秋；自研对端可全程 UTF-8 + UTF8OPT。
- **端口占用**：手机上 2425 一般空闲；若被占用要可配置（飞秋 `FeiqPortNo` 也可改）。

## 八、建议的开发里程碑

1. **M1 互相发现**：UDP 收发 + 广播，安卓能在飞秋列表里出现、也能看到飞秋。（验证 `BR_ENTRY/ANSENTRY`）
2. **M2 文字互通**：`SENDMSG` + 回执 + 重发，安卓↔飞秋互发文字。（最小可用）
3. **M3 文件互传**：TCP `GETFILEDATA` 单文件双向 + 续传。
4. **M4 文件夹/图片**：`GETDIRFILES` + 图文。
5. **M5 完整复刻**：飞秋私有扩展（头像/签名/富文本/表情）抓包对齐；可选加密。

> 自研 PC 对端可与安卓端共用同一套协议常量，先用标准 IPMsg 把两端打通，再逐步贴近飞秋。
